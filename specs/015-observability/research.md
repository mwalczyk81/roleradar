# Phase 0 Research: End-to-End Observability and Local Telemetry Dev Loop (`015-observability`)

**Date**: 2026-11-11
**Feature**: [spec.md](./spec.md)
**Epic / Issues**: `RR-66` (`RR-67` to `RR-72`, `RR-86`)

## R-001: Native MongoDB Driver Tracing vs. Third-Party Instrumentation Package

- **Decision**: Use `MongoDB.Driver` 3.13.0's built-in `MongoDB.Driver.MongoTelemetry` (`ActivitySource` name `"MongoDB.Driver"`) and `MongoClientSettings.TracingOptions` (`Disabled = false`, `QueryTextMaxLength = 0`), subscribed by name in `RoleRadar.Observability`. Do not add `MongoDB.Driver.Core.Extensions.DiagnosticSources`.
- **Rationale**:
  - Inspection of the pinned `MongoDB.Driver` `3.13.0` assembly confirms it natively emits OpenTelemetry database spans on `ActivitySource("MongoDB.Driver")` with standard OpenTelemetry attributes (`db.system.name = "mongodb"`, `db.operation.name`, `db.command.name`, `db.namespace`, `db.collection.name`, `server.address`, `server.port`, `db.response.status_code`).
  - By default, `TracingOptions.Disabled` is `false` and `TracingOptions.QueryTextMaxLength` is `0`, meaning the driver omits `db.query.text` (raw BSON command documents, note `content`, `ruleText`, and filter literals) unless explicitly asked to include it. Setting `settings.TracingOptions = new TracingOptions { Disabled = false, QueryTextMaxLength = 0 }` explicitly in `ConnectionStringRedactor.CreateClient` pins this privacy guarantee in code.
  - Subscribing via `.AddSource("MongoDB.Driver")` in `RoleRadar.Observability` requires zero `MongoDB.*` package references in `RoleRadar.Observability`, keeping `ObservabilityArchitectureTests.Observability_ReferencesNoAspNetMongoOrDuende` green.
- **Alternatives considered**:
  - `MongoDB.Driver.Core.Extensions.DiagnosticSources` `3.0.0` (Apache-2.0, published 2025-11-30): Third-party diagnostic subscriber written before the official driver added native `ActivitySource` support. Redundant with `MongoDB.Driver` 3.13.0's native `MongoTelemetry`.

## R-002: .NET 10 Native Platform Telemetry vs. `OpenTelemetry.Instrumentation.*` Packages

- **Decision**: Wire OpenTelemetry in `RoleRadar.Observability` using `OpenTelemetry` (`1.20.1`), `OpenTelemetry.Extensions.Hosting` (`1.20.1`), and `OpenTelemetry.Exporter.OpenTelemetryProtocol` (`1.20.1`) (plus `OpenTelemetry.Exporter.InMemory` `1.20.1` in test projects), subscribing directly to .NET 10's built-in `ActivitySource`s (`"Microsoft.AspNetCore"`, `"System.Net.Http"`, `"MongoDB.Driver"`, `"RoleRadar"`) and built-in `Meter`s (`"Microsoft.AspNetCore.Hosting"`, `"Microsoft.AspNetCore.Server.Kestrel"`, `"Microsoft.AspNetCore.Routing"`, `"Microsoft.AspNetCore.Diagnostics"`, `"Microsoft.AspNetCore.RateLimiting"`, `"System.Net.Http"`, `"System.Net.NameResolution"`, `"System.Runtime"`, `"RoleRadar.Store"`).
- **Rationale**:
  - All selected OpenTelemetry .NET packages (`1.20.1`) are Apache-2.0 and were published on `2026-10-20` (22 days before `2026-11-11`, satisfying the `>= 14`-day release-age rule; `1.21.0` published `2026-11-11` is excluded as too new).
  - Inspection of .NET 10's `Microsoft.AspNetCore.Hosting.dll`, `System.Net.Http.dll`, and `System.Diagnostics.DiagnosticSource.dll` confirms that .NET 10 natively emits OpenTelemetry semantic conventions for HTTP server spans/metrics (`http.server.request.duration`, `http.server.active_requests`, `url.path` without `url.query`), HTTP client spans/metrics (`http.client.request.duration`, `url.full` with query values redacted by default), and .NET runtime metrics (`System.Runtime`: `dotnet.process.cpu.time`, `dotnet.process.memory.working_set`, `dotnet.gc.*`, `dotnet.thread_pool.*`, `dotnet.exceptions`).
  - `OpenTelemetry.Instrumentation.AspNetCore` declares `<FrameworkReference Include="Microsoft.AspNetCore.App" />`, which would violate `ObservabilityArchitectureTests.Observability_ReferencesNoAspNetMongoOrDuende` if added to `RoleRadar.Observability` (referenced by non-web hosts `RoleRadar.Cli` and `RoleRadar.Mcp.Stdio`). Subscribing by source and meter name in `RoleRadar.Observability` lets `Api` and `Identity` share one setup in `RoleRadar.Observability` with zero architecture test compromises.
- **Alternatives considered**:
  - Referencing `OpenTelemetry.Instrumentation.AspNetCore` `1.20.1`, `OpenTelemetry.Instrumentation.Http` `1.20.1`, and `OpenTelemetry.Instrumentation.Runtime` `1.20.1` separately in each host: Duplicates telemetry wiring across `Api` and `Identity` or forces `RoleRadar.Observability` to depend on `Microsoft.AspNetCore.App`, for sources and meters that .NET 10 already provides in the shared framework.

## R-003: Web OpenTelemetry SDK and Replacing Manual `trace-context.server.ts` Wiring ("One Mechanism, Not Two")

- **Decision**: Adopt the `2026-10-20` OpenTelemetry JS release wave (`@opentelemetry/sdk-trace` `3.0.0`, `@opentelemetry/context-async-hooks` `3.0.0`, `@opentelemetry/resources` `3.0.0`, `@opentelemetry/sdk-logs` `3.0.0`, `@opentelemetry/sdk-metrics` `3.0.0`, `@opentelemetry/exporter-trace-otlp-http` `0.300.0`, `@opentelemetry/exporter-logs-otlp-http` `0.300.0`, `@opentelemetry/exporter-metrics-otlp-http` `0.300.0`, `@opentelemetry/instrumentation-http` `0.300.0`, `@opentelemetry/instrumentation-undici` `0.34.0`, and `@opentelemetry/semantic-conventions` `1.44.0` published `2026-10-28`) on top of the existing `@opentelemetry/api` `1.10.0` and `@opentelemetry/core` `3.0.0`. Replace the manual `randomHex` ID generator and manual `trace.setSpanContext` in `web/app/lib/trace-context.server.ts` with the registered OpenTelemetry `BasicTracerProvider` / `AsyncLocalStorageContextManager` and global `W3CTraceContextPropagator`.
- **Rationale**:
  - Every package in the `2026-10-20` / `2026-10-28` wave is Apache-2.0, at least 14 days old as of `2026-11-11` (`0.301.x` / `3.1.x` from `2026-11-05` and `2026-11-09` are excluded as `< 14` days old), and matches the already-pinned `@opentelemetry/api@1.10.0` and `@opentelemetry/core@3.0.0`.
  - In `@opentelemetry/api` `1.10.0` and `@opentelemetry/sdk-trace` `3.0.0`, registering `AsyncLocalStorageContextManager` and `W3CTraceContextPropagator` globally allows `startTrace` at the web edge (`web/server.ts`) to extract the validated inbound `traceparent` via `propagation.extract`, start an active server span via `trace.getTracer("roleradar-web").startActiveSpan(...)`, and read `span.spanContext().traceId` and `spanId` directly from the SDK span. Outbound `withTraceparent(headers)` delegates directly to `propagation.inject(context.active(), headers)`.
  - Only the 5-line strict 55-character lowercase pre-check before `propagation.extract` remains so Feature 014's edge validation contract (`trace-context.test.ts`: reject uppercase hex in version/flags and oversized headers) holds. The manual `randomBytes` loop and manual root span context construction are deleted—leaving **one mechanism, not two**.
- **Alternatives considered**:
  - Keeping `trace-context.server.ts`'s manual `newTraceId()` / `newSpanId()` alongside the OpenTelemetry Node SDK: Rejected by the owner's "One mechanism, not two" rule because two parallel trace context mechanisms can drift on span IDs and require an ADR to justify duplication.

## R-004: Span Attribute Allowlist/Drop-List Processor (`ADR 0050`, Gate 2) vs. Runtime Log Scrubbing (`RR-86`, `ADR 0051`, Gate 3)

- **Decision**:
  1. **Gate 2 Span Sanitization (`ADR 0050`)**: Use a `LogScrubber`-independent allowlist and drop-list span processor (`RoleRadarSpanAttributeProcessor` in `.NET` and `WebSpanAttributeProcessor` in `web/`), recorded in `docs/adr/0050-span-attribute-allowlist-processor.md`. It removes `url.query`, strips query/fragment parts from `url.full` (and legacy `http.url`/`http.target`), removes all request/response headers (`http.request.header.*`, `http.response.header.*`), removes `db.query.text` / `db.statement`, drops any non-allowlisted span attribute, and sanitizes span `exception` events by keeping only `exception.type` (and mapping to `error.type`), dropping `exception.message` and `exception.stacktrace`, and clearing free-text `StatusDescription`. This makes Gate 2 stand completely independent of `RR-86`'s outcome in Gate 3.
  2. **Gate 3 Runtime Log Scrubbing & OTLP Log Pipeline (`RR-86` / `RR-70`, `ADR 0051`)**: Execute the evidence-first `RR-86` evaluation in Gate 3 (`docs/adr/0051-otel-logs-and-runtime-scrubbing.md`), mapping each of the seven `LogScrubber` rules to a concrete producer in the stack, testing whether an OpenTelemetry `BaseProcessor<LogRecord>` (`OnEnd(LogRecord)`) can scrub formatted messages, structured attributes, and exception text, comparing the OTLP log data model against the Feature 013 console record contract (ADR 0047), and recording the architectural outcome in `ADR 0051`.
- **Rationale**:
  - Decoupling Gate 2's span privacy processor from `LogScrubber` avoids presupposing the Gate 3 (`RR-86`) decision on whether `LogScrubber` stays, shrinks, moves into a log processor, or goes.
  - Span attributes follow a closed set of OpenTelemetry HTTP and database semantic conventions (`http.request.method`, `url.scheme`, `url.path`, `url.full` without query/fragment, `http.route`, `http.response.status_code`, `server.address`, `server.port`, `network.protocol.version`, `error.type`, `db.system.name`, `db.operation.name`, `db.command.name`, `db.namespace`, `db.collection.name`, `db.response.status_code`), so a structural allowlist/drop-list + stripping raw exception text on spans is stronger, faster, and regex-free.
  - For logs in Gate 3 (`ADR 0051`), ADR 0046 proved that `Microsoft.Extensions.Compliance.Redaction` cannot redact third-party messages, query strings, or exceptions, and ADR 0047 noted that `ILoggingBuilder.AddOpenTelemetry` is a clean `ILoggerProvider` addition (`IncludeFormattedMessage = true`, `IncludeScopes = true`). Gate 3 (`RR-86` + `RR-70`) tests `LogRecord` exception and body scrubbing directly in a scratch spike and in the `RR-72` log privacy gate.
- **Alternatives considered**:
  - Coupling Gate 2's span processor to `LogScrubber`: Rejected because `RR-86` decides `LogScrubber`'s fate in Gate 3, and span attributes are structural tags rather than free-text log lines.
  - External OpenTelemetry Collector `transform`/`redaction` processor: Rejected under Principle X (`ADR 0050`) because unredacted query strings, headers, or exception messages would leave the application process before scrubbing and would not protect direct OTLP export when no intermediate collector container is present.
  - Serilog + `Serilog.Sinks.OpenTelemetry`: Rejected in ADR 0047 and here because all RoleRadar hosts log exclusively through `ILogger` (`22` `LoggerMessage` definitions), and `ILoggingBuilder.AddOpenTelemetry` bridges `ILogger` directly to OTLP without introducing a second logging framework.

## R-005: Local Observability Setup (`RR-67` Spike, `ADR 0049`, and `RR-71` Implementation)

- **Decision**: Gate 1 (`RR-67`) runs a scratch spike with fictional data and throwaway containers and commits `ADR 0049` (docs only) evaluating `.NET Aspire` (`Aspire.Hosting.AppHost` `13.6.4`, `Aspire.Hosting.MongoDB` `13.6.4`, `Aspire.Hosting.JavaScript` `13.6.4`, all published `2026-10-24`, MIT license) + Aspire Dashboard (`mcr.microsoft.com/dotnet/aspire-dashboard:13.6.4@sha256:23411f715be2476da0b2c0ad110039237de657c6cae31bf5c587d12a26c11230`) against Seq, Jaeger, and Grafana LGTM. If the spike confirms Option 2 (Aspire AppHost + Dashboard) reproduces replica-set MongoDB and Identity's issuer URLs and TLS, Gate 5 (`RR-71`) implements `src/RoleRadar.AppHost`; if the spike finds a blocker on either requirement, `ADR 0049` records the blocker and Gate 5 implements the fallback: the standalone Aspire Dashboard in an opt-in Docker Compose overlay (`deploy/docker-compose.telemetry.yml`).
- **Rationale**:
  - `Aspire.Hosting.*` `13.6.4` (published `2026-10-24`, 18 days old; `13.6.5` from `2026-11-10` is excluded as `< 14` days old) and `mcr.microsoft.com/dotnet/aspire-dashboard:13.6.4@sha256:23411f715be2476da0b2c0ad110039237de657c6cae31bf5c587d12a26c11230` provide an MIT-licensed, single-binary/single-container OTLP collector and UI for traces, structured logs, metrics, and resource graphs bound to `127.0.0.1` with zero telemetry leaving the machine.
  - RoleRadar requires MongoDB to run as a replica set (`--replSet rs0`) for multi-document transactions, and Identity + API + Web use `https://identity:5001` (or matching SAN certificates) for OIDC discovery/JWKS and browser redirects. Checking these in Gate 1 before touching repo code eliminates rework risk.
  - The Aspire Dashboard provides built-in views (traces, structured logs, metrics, resource graph) and does not support custom saved dashboards; `ADR 0049` confirms this and records that custom saved dashboards belong to a future hosted backend.
  - Option 3 (using the AppHost as the single orchestration and deployment artifact publisher, e.g., for Azure Container Apps via `azd`) is explicitly recorded in `ADR 0049` as deferred until hosting is un-parked.
- **Alternatives considered**:
  - **Seq**: Proprietary license (free single-user tier, not OSI open-source), primarily a log/trace viewer without full OTLP metrics and resource graph parity.
  - **Jaeger**: Apache-2.0, strong trace viewer, but does not natively provide unified OTLP structured log and metric views in one lightweight UI.
  - **Grafana LGTM (`otel-lgtm` / Loki + Grafana + Tempo + Mimir)**: Heavy multi-component container footprint for a local dev loop; overkill until saved custom dashboards and alerting are needed in a hosted environment.

## R-006: Compose vs. AppHost Drift Prevention, Layering, and CI Cost

- **Decision**: Enforce drift prevention and layering inside the existing `tests/RoleRadar.Tests.Architecture` project (`AppHostComposeParityArchitectureTests`, `LayerDependencyArchitectureTests`, `ObservabilityArchitectureTests`). Do not add a new test project, do not add a custom script, and do not start the AppHost in CI.
- **Rationale**:
  - An xUnit test in `RoleRadar.Tests.Architecture` parses `deploy/docker-compose.yml` and `deploy/docker-compose.apps.yml` and compares ports (`5001`, `5002`, `5003`, `27017`), required environment variables, pinned `mongo:9.0.4` image, and volume isolation (forbidding `roleradar-mongo-data` and `roleradar-identity-data` in the local telemetry setup) against the AppHost/overlay definition.
  - It runs in milliseconds during `pwsh ./scripts/test-fast.ps1` and the existing CI build/test step, adding zero heavy container lanes to CI.
  - `LayerDependencyArchitectureTests` and `ObservabilityArchitectureTests` enforce that `RoleRadar.AppHost` (when Option 2 is active) may reference `RoleRadar.Api` and `RoleRadar.Identity`, may not directly reference `Duende.*` packages, and no other project in `src/` may reference `RoleRadar.AppHost`.
- **Alternatives considered**:
  - A custom PowerShell or Node drift script: Rejected per `AGENTS.md` ("Prefer an existing tool or GitHub Action to a new custom script; a new script needs a one-line justification in the spec").
  - Starting the AppHost in a new CI Testcontainers lane: Rejected per owner instruction ("CI cost. Do not add a heavy lane. The AppHost need not start in CI. A build check plus the drift test is enough").
