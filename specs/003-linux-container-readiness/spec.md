# Feature Specification: Linux Container Readiness for Azure-Style Hosting

**Feature Branch**: `003-linux-container-readiness`

**Created**: 2026-10-18

**Status**: Draft

**Input**: User description: "Linux container readiness for Azure-style hosting: multi-stage Linux images (linux/amd64 and linux/arm64) for CLI and stdio MCP server, non-root, read-only rootfs, no network listeners, no Docker socket, bundled MongoDB Database Tools for backup/restore across all 12 collections; hosting-readiness conventions enforced by tests (env config, no writes outside configured dirs, stderr logs, SIGTERM shutdown, UTC, no Windows path assumptions, redacted connection strings); existing launched-host tests run against images; external-Mongo compatibility checklist mode for Contract test suite; cross-platform scripts and pre-commit hooks (Windows, macOS, Linux) with macOS CI job; supply-chain hygiene (digest-pinned base images, hadolint, vuln scan with zero critical vulns, SBOM, private-data exclusion); ADRs for hosted MongoDB options and Azure runtime target."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Secure Linux Container Images for CLI and MCP Host (Priority: P1)

As a system owner preparing for cloud hosting and cross-platform use, I want hardened, multi-stage Linux container images for both the command-line interface (CLI) and the stdio Model Context Protocol (MCP) server so that both tools can run in isolated, rootless, immutable environments on any Linux container host (x86_64 and ARM64) without host-system dependencies.

**Why this priority**: Foundational container artifacts are required before hosting readiness, automated image testing, or cloud runtime selection can be verified.

**Independent Test**: Can be tested independently by building the images on Linux/amd64 and Linux/arm64 and running `docker run -i --rm` to execute CLI commands and MCP stdio protocol handshakes under a non-root user and read-only root filesystem.

**Acceptance Scenarios**:

1. **Given** a built CLI container image, **When** executed with `--help` or `status` with a read-only root filesystem, **Then** the container executes as a non-privileged user (non-root), emits output to standard output, logs to standard error, opens no network listeners, and exits cleanly with code 0.
2. **Given** a built MCP stdio container image, **When** launched in interactive mode (`docker run -i --rm`) with standard input connected to an MCP client, **Then** it initializes the MCP session over standard input/output without binding any network port, runs as a non-root user with a read-only root filesystem, and handles protocol commands idempotently.
3. **Given** either container image, **When** inspected for user privileges and network configuration, **Then** the container runs under a designated non-root UID/GID, exposes zero listening network ports (`EXPOSE`), and mounts no Docker socket.

### User Story 2 - Hosting-Readiness Conventions Enforced by Automated Verification (Priority: P1)

As a maintainer, I want automated test suites to enforce production hosting conventions across all host processes so that future cloud container deployments (such as Azure Container Apps or Kubernetes) operate predictably and safely without platform-specific assumptions.

**Why this priority**: Catching hosting anti-patterns (hardcoded paths, credential leakage, stdout corruption, unhandled signals) via automated tests prevents production runtime failures and security vulnerabilities before HTTP services are introduced.

**Independent Test**: Can be tested by running automated architecture and process-level tests that assert environment-only configuration, standard-error-only logging, signal termination compliance, UTC time generation, and connection string masking.

**Acceptance Scenarios**:

1. **Given** any host process (CLI or MCP), **When** configuration is supplied exclusively via environment variables, **Then** the application starts and functions without requiring local configuration files in the working directory.
2. **Given** an MCP host process, **When** any informational, debug, or diagnostic event is emitted, **Then** it is written strictly to standard error, ensuring standard output contains only valid protocol frames.
3. **Given** a running host process, **When** a `SIGTERM` signal is delivered, **Then** the process initiates a graceful shutdown, completes in-flight work, releases resources, and terminates within a bounded shutdown timeout.
4. **Given** an invalid or failing database connection string containing plaintext passwords or user credentials, **When** connection failure diagnostics or errors are logged, **Then** user credentials, secrets, and sensitive tokens are fully redacted from all outputs, standard error, and exception messages.
5. **Given** any timestamp generated by the system across all entities and audit entries, **When** recorded or formatted, **Then** the timestamp is strictly in Coordinated Universal Time (UTC).

### User Story 3 - Self-Contained Database Backup, Restore, and Wipe Inside the CLI Container (Priority: P1)

As an operator, I want database backup, restore, and wipe commands to execute completely inside the CLI container against any reachable database host without mounting the host Docker socket or invoking host-level tools, while protecting all 12 system collections.

**Why this priority**: Eliminates Docker-out-of-Docker security hazards, enabling scheduled backup jobs in rootless cloud container environments (e.g., Azure Container Apps jobs) against remote managed databases.

**Independent Test**: Can be tested by running `roleradar backup`, `restore`, and `wipe` commands entirely inside the CLI container against an isolated database service across all 12 collections, verifying that no host docker socket or external binary is required.

**Acceptance Scenarios**:

1. **Given** a database containing documents across all 12 collections (notes, note revisions, audit log, companies, career sources, criteria, postings, posting signals, applications, application events, contacts, search runs), **When** `roleradar backup` is executed inside the container specifying a mounted output path, **Then** it produces an encrypted backup archive covering all 12 collections directly using bundled tools without contacting a Docker daemon.
2. **Given** a valid encrypted backup archive, **When** `roleradar restore` is executed inside the container against a clean database, **Then** all 12 collections are fully restored with identical document counts, indexes, and content integrity, reporting restored counts per collection.
3. **Given** an existing populated database, **When** `roleradar wipe --yes` is executed inside the container, **Then** all documents across all 12 collections are deleted, collections are reset, and a detailed summary of removed records is reported.

### User Story 4 - Launched-Host Test Parity Against Container Images (Priority: P1)

As a quality engineer, I want the full suite of end-to-end launched-host tests to execute identically against the built Linux container images so that behavior in containers is proven equivalent to native binary execution.

**Why this priority**: Ensures that containerization introduces zero regressions in protocol framing, concurrency safety, data privacy, or tool schemas.

**Independent Test**: Can be tested by executing the existing startup smoke tests, concurrency race tests, PII/contact no-leak scans, and tool-schema contract tests targeting containerized host invocations (`docker run`).

**Acceptance Scenarios**:

1. **Given** the built container images, **When** the startup smoke test suite executes, **Then** all CLI subcommands and MCP protocol initialization commands succeed with expected exit codes and clean output streams.
2. **Given** the built MCP container image, **When** concurrent container processes execute search run logging simultaneously, **Then** database unique constraints and idempotency guarantees hold exactly as in native execution (exactly one record created, duplicates report existing status).
3. **Given** the built container images, **When** a contact with distinctive fictional details is created and system commands (status, verify, backup, MCP tool listing, error generation) are executed, **Then** the confidential contact details appear nowhere in standard output, standard error, logs, or unencrypted backup archives except when specifically retrieved via `contact get`.
4. **Given** the built MCP container image, **When** the tool-schema contract test suite runs, **Then** the tool count is verified to be exactly 12 with identical schemas and descriptions.

### User Story 5 - Hosted Database Compatibility Matrix & Validation Mode (Priority: P2)

As an architect evaluating cloud databases, I want to execute the storage contract test suite against an external MongoDB endpoint so that candidate cloud services (such as Azure Cosmos DB vCore or MongoDB Atlas) can be verified for transaction, partial index, and text search compatibility, producing an actionable pass/fail capability matrix.

**Why this priority**: Identifies any functional discrepancies or unsupported database features in cloud managed databases prior to infrastructure provisioning and deployment.

**Independent Test**: Can be tested by providing an external database connection string to a dedicated test runner mode, verifying safety guards, running the contract suite, and inspecting the generated capability report.

**Acceptance Scenarios**:

1. **Given** an external database connection string, **When** the compatibility test suite is initiated against an endpoint that is not empty or lacks explicit test authorization markers, **Then** the test runner immediately aborts with a clear safety warning without modifying or querying non-test data.
2. **Given** an authorized empty external database endpoint, **When** the compatibility suite executes, **Then** it runs isolated tests across unique per-test database names, verifies multi-document cross-collection transactions, partial unique indexes, and text search, and thoroughly cleans up all test databases upon completion.
3. **Given** the completion of the compatibility test run, **When** test results are compiled, **Then** the system outputs a structured pass/fail capability matrix detailing each evaluated database invariant (transactions, unique indexes, text search) to inform architectural decisions.

### User Story 6 - Cross-Platform Automation & Multi-OS CI Verification (Priority: P2)

As a developer working across different operating systems, I want all repository scripts, automation tools, and pre-commit hooks to run seamlessly on Windows, macOS, and Linux, and to have continuous integration verify pull requests across all three platforms.

**Why this priority**: Prevents platform drift, broken developer scripts, and path-separator failures when collaborating or deploying across multi-OS environments.

**Independent Test**: Can be tested by running the entire script suite and pre-commit checks on Windows, Linux, and macOS environments, and verifying that CI executes dedicated jobs for Windows, Ubuntu, and macOS.

**Acceptance Scenarios**:

1. **Given** any repository script (service startup, test runners, build scripts, formatting, analysis), **When** executed using PowerShell (`pwsh`) on Windows, macOS, or Linux, **Then** the script completes successfully without path separator errors, backslash assumptions, or environment-specific failures.
2. **Given** the local pre-commit guard, **When** executed on macOS or Linux, **Then** it properly resolves the external privacy denylist from standard OS configuration directories (e.g., `~/.config/roleradar/denylist.txt`) without assuming Windows `LOCALAPPDATA`.
3. **Given** a pull request or push to the repository, **When** the CI workflow runs, **Then** automated build and test jobs execute and pass across Windows, Ubuntu Linux, and macOS runners.

### User Story 7 - Supply Chain Hardening & Container Vulnerability Governance (Priority: P2)

As a security auditor, I want container base images pinned to immutable cryptographic digests, Dockerfiles linted against security standards, and container images scanned for vulnerabilities and sensitive data leakage so that the software supply chain is verifiable and secure.

**Why this priority**: Minimizes attack surfaces, prevents image tampering or drift, and ensures zero critical vulnerabilities enter deployment pipelines.

**Independent Test**: Can be tested by running Dockerfile linting (e.g., `hadolint`), container vulnerability scanning (e.g., `trivy`), and scanning container filesystem and history for private data or sensitive file inclusion.

**Acceptance Scenarios**:

1. **Given** the project Dockerfiles, **When** inspected or linted, **Then** all base images are pinned by sha256 cryptographic digests, instructions follow non-root and minimal-privilege standards, and the linter passes with zero warnings or errors.
2. **Given** the built container images, **When** subjected to container vulnerability scanning, **Then** zero critical-severity vulnerabilities are reported.
3. **Given** the container build context and built images, **When** scanned for sensitive files, developer secrets, or private data matches, **Then** zero unauthorized files or sensitive data traces exist in the image layers or filesystem history.
4. **Given** the build pipeline, **When** container images are generated, **Then** a Software Bill of Materials (SBOM) is produced documenting all included packages and dependencies.

### User Story 8 - Cloud Hosting & Database Architecture Decision Records (Priority: P3)

As a technical lead, I want documented Architecture Decision Records (ADRs) evaluating candidate cloud database options and Azure container runtime environments against our verified compatibility matrix so that future hosting choices are well-justified, transparent, and recorded.

**Why this priority**: Solidifies architectural consensus and documents trade-offs prior to committing time and infrastructure costs to cloud deployments.

**Independent Test**: Can be tested by reviewing the committed MADR documents under `docs/adr/` ensuring all decision criteria, trade-offs, and compatibility results are comprehensively addressed.

**Acceptance Scenarios**:

1. **Given** candidate cloud database options (MongoDB Atlas on Azure, Azure Cosmos DB for MongoDB vCore, self-hosted containerized MongoDB with persistent storage), **When** evaluated in a formal ADR, **Then** the record documents their support for cross-collection transactions, partial unique indexes, text search, operational complexity, and pricing tiers against our compatibility checklist.
2. **Given** candidate Azure container runtimes (Azure Container Apps vs. Azure Kubernetes Service), **When** evaluated in a formal ADR, **Then** the record analyzes operational trade-offs, scale-to-zero capabilities, secret management, job scheduling for backups, and migration path for future HTTP services.
3. **Given** the completion of both ADRs, **When** reviewed, **Then** neither record initiates cloud provisioning or requires live cloud infrastructure deployments in this feature phase.

### Edge Cases

- **Read-Only Root Filesystem Restrictions**: How does the container handle temporary file generation or tool cache writes when rootfs is strictly read-only? The container configuration must explicitly define and mount designated ephemeral temporary volumes (e.g. `/tmp`) with restricted permissions.
- **Malformed or Credential-Heavy Connection Strings**: What happens if an external connection string contains unencoded special characters or multiple authentication parameters? The connection parser must safely extract target hosts while ensuring credentials are never exposed in log output or error traces.
- **External Database Non-Empty Collision**: What happens if an external MongoDB endpoint provided for compatibility testing already contains data or non-test collections? The test runner must refuse execution immediately to prevent any risk of data loss or test corruption.
- **Unsupported Database Feature Encountered**: How does the compatibility suite behave when a candidate hosted database returns an error for cross-collection transactions or partial indexes? The suite must isolate the failure, record the specific diagnostic reason in the compatibility matrix, and continue testing remaining capabilities without crashing.
- **Abrupt Process Termination (SIGTERM / SIGINT)**: What happens if a containerized backup or restore process receives a termination signal midway through execution? The container process must catch the signal, flush diagnostic logs to standard error, terminate in-flight child processes, clean up incomplete temporary archives, and exit cleanly without leaving stale locks.
- **Standard Input Disconnect in MCP Host**: What happens when an MCP client closes the stdio pipe unexpectedly? The MCP server container must detect EOF on standard input and exit cleanly with code 0 without hanging or spinning CPU.
- **Missing Denylist on Non-Windows Hosts**: What happens if a developer on macOS or Linux runs pre-commit checks before creating an external denylist file? The hook must report a helpful, platform-appropriate setup instruction indicating the expected configuration path rather than crashing with a path resolution exception.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide multi-stage Dockerfiles producing minimal, hardened Linux container images for both the RoleRadar CLI and the stdio MCP server.
- **FR-002**: Container images MUST support both `linux/amd64` and `linux/arm64` CPU architectures natively without functional discrepancies.
- **FR-003**: Container images MUST run under an unprivileged non-root user account with a fixed UID/GID and MUST operate reliably with a read-only root filesystem (`--read-only`).
- **FR-004**: The stdio MCP container image MUST NOT declare or bind any network listening ports, reserving standard output exclusively for MCP protocol JSON-RPC messages and standard error for diagnostic logging.
- **FR-005**: All host applications (CLI and MCP server) MUST support full operational configuration exclusively through environment variables, requiring no local configuration files in the working directory.
- **FR-006**: The CLI container image MUST bundle native MongoDB Database Tools (`mongodump`, `mongorestore`) directly within the image, eliminating any requirement for a host Docker socket, `docker exec`, or host-installed database utilities.
- **FR-007**: The containerized backup command (`roleradar backup`) MUST execute against any reachable MongoDB connection string and produce an encrypted, authenticated archive covering all 12 system collections (notes, note_revisions, audit_log, companies, career_sources, criteria, postings, posting_signals, applications, application_events, contacts, search_runs).
- **FR-008**: The containerized restore command (`roleradar restore`) MUST verify archive integrity and restore all 12 collections with exact document, index, and schema fidelity against an empty database.
- **FR-009**: The containerized wipe command (`roleradar wipe`) MUST refuse to run without explicit user confirmation and, upon confirmation, purge all documents across all 12 collections while emitting an itemized removal count.
- **FR-010**: All host processes MUST intercept `SIGTERM` and `SIGINT` signals, perform graceful cleanup of active connections and child processes, and terminate within a configurable grace period.
- **FR-011**: All host processes MUST sanitize connection strings, tokens, and credentials in all exception messages, logs, diagnostic outputs, and traces, completely masking passwords and sensitive parameters.
- **FR-012**: All timestamps created, stored, or processed by the system MUST be strictly in Coordinated Universal Time (UTC).
- **FR-013**: The system MUST provide an external database compatibility test mode for the storage contract test suite, allowing validation against an external MongoDB endpoint specified by an environment variable.
- **FR-014**: The external database compatibility test runner MUST enforce strict safety guards, immediately refusing execution if the target endpoint is not empty or lacks explicit test authorization markers.
- **FR-015**: The external database compatibility test runner MUST isolate individual test fixtures using uniquely generated, ephemeral database names and MUST automatically drop all test databases upon test completion.
- **FR-016**: The compatibility test suite MUST generate a structured, machine-readable and human-readable capability matrix detailing test outcomes for multi-document cross-collection transactions, partial unique indexes, and text search.
- **FR-017**: All repository automation scripts (PowerShell `/scripts`) MUST execute without error across Windows, Linux, and macOS environments, using platform-agnostic path handling and avoiding Windows-specific backslash assumptions.
- **FR-018**: The local pre-commit guard MUST resolve the external confidential denylist file from platform-appropriate standard configuration paths on Windows, macOS, and Linux.
- **FR-019**: Continuous integration (CI) workflows MUST include automated build, lint, and test jobs running on Windows, Ubuntu Linux, and macOS runners.
- **FR-020**: Base container images in Dockerfiles MUST be cryptographically pinned using immutable `sha256` digests rather than floating tags.
- **FR-021**: Dockerfile definitions MUST adhere to best practice container linting rules verified via automated linting in CI.
- **FR-022**: Built container images MUST be verified by automated vulnerability scanning in CI, achieving a policy of zero critical-severity security vulnerabilities.
- **FR-023**: Container build configurations MUST utilize strict build-ignore rules (`.dockerignore`) to ensure private data, local test results, git history, and secrets are excluded from image contexts.
- **FR-024**: Automated tests MUST scan the filesystem and layer history of built container images to verify zero occurrences of confidential denylist terms, personal data, or unauthorized files.
- **FR-025**: The build process MUST generate a comprehensive Software Bill of Materials (SBOM) for each produced container image.
- **FR-026**: The existing launched-host test suite (startup smoke, concurrency race tests, contact privacy no-leak scans, and tool-schema contracts) MUST be extended to execute against the built container images with 100% pass rate.
- **FR-027**: The project MUST document an Architectural Decision Record (MADR) evaluating cloud MongoDB hosting options (MongoDB Atlas on Azure, Azure Cosmos DB for MongoDB vCore, and self-hosted containerized MongoDB with persistent storage) against the compatibility checklist.
- **FR-028**: The project MUST document an Architectural Decision Record (MADR) evaluating Azure container runtime targets (Azure Container Apps vs. Azure Kubernetes Service) for future workload hosting.
- **FR-029**: In-container diagnostic logging across all processes MUST be directed to standard error, ensuring standard output remains unpolluted for CLI output and protocol framing.
- **FR-030**: Container cold-start performance MUST be verified by automated benchmark tests ensuring rapid initialization suitable for on-demand execution.

### Key Entities

- **Container Image Specification**: Defines the multi-stage build, base image digests, non-root user permissions, read-only root filesystem constraints, and bundled runtime dependencies for the CLI and MCP host images.
- **Hosted Database Compatibility Matrix**: A structured assessment artifact detailing the operational status and pass/fail results for critical database capabilities (cross-collection transactions, partial unique indexes, text search) against candidate database engines.
- **Database Safety Guard Descriptor**: Configuration rules and validation logic that inspect a target database endpoint before test execution to ensure it is isolated, authorized, and safe for ephemeral test operations.
- **Supply Chain Security Profile**: A collection of compliance artifacts including Dockerfile lint reports, vulnerability scan results, SBOM inventories, and image layer privacy scans.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Filesystem and commit history scanning of built container images and repository contents reports **zero matches** against confidential denylist terms and private data patterns.
- **SC-002**: Automated vulnerability scanning of both built container images reports **zero critical-severity vulnerabilities**.
- **SC-003**: The cold start duration of the MCP stdio container—measured from container launch (`docker run`) to receipt of the first valid JSON-RPC tool response—is **under 3.0 seconds** on standard CI runner infrastructure.
- **SC-004**: **100%** of the existing launched-host test suite (including startup smoke tests, concurrency race tests, contact privacy no-leak tests, and the 12-tool schema contract test) passes without modification when targeting the container images on both `linux/amd64` and `linux/arm64`.
- **SC-005**: Executing the database compatibility test suite against an external MongoDB endpoint produces a comprehensive pass/fail checklist itemizing transaction, index, and search capabilities, with **zero unintentional mutations** to non-test databases.
- **SC-006**: The full automated test suite and developer automation scripts pass cleanly with **zero platform-specific failures** across all three major operating systems (Windows, Ubuntu Linux, macOS) in CI.
- **SC-007**: Complete database backup, restore, and wipe operations covering all 12 system collections execute successfully inside the CLI container with **zero dependency** on a host Docker daemon or host Docker socket.
- **SC-008**: Two formal Architecture Decision Records (MADRs) covering hosted database options and cloud container runtime targets are completed and committed under `docs/adr/`.

## Assumptions

- The target deployment model for future HTTP services (004 API/web, 005 MCP over HTTP) will utilize Linux containers in Azure; this feature establishes baseline containerization and hosting readiness without deploying cloud resources.
- Container execution environments support Open Container Initiative (OCI) image standards and allow mounting ephemeral volumes for temporary file operations when the root filesystem is read-only.
- Bundled native database tools (`mongodump` and `mongorestore`) maintain protocol compatibility with MongoDB version 7.0 and compatible wire-protocol endpoints.
- External database compatibility testing requires a reachable database connection string supplied via a secure environment variable during test runs; if not provided, the test suite defaults to local ephemeral Testcontainers.
- The single-owner, local-first security and privacy model (Principle I and Principle VII) continues to govern all operations, requiring encrypted backups and strict isolation of confidential contact information.
- No public network-listening endpoints (HTTP, WebSockets) are deployed or exposed in this feature phase.
