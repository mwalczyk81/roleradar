# Feature Specification: Front Door (public-repo showpiece pass)

**Feature Branch**: `012-front-door`

**Created**: 2026-11-08

**Status**: Draft

**Input**: User description: "Feature 012, front door: a one-command fictional demo with a throwaway login, screenshots from it, a README rewrite with the files around it, a first release's changelog, and local pre-announce safety checks."

## Why

A stranger who lands on the repository cannot tell that there is a polished product. The README has no screenshots and no badges, and its diagram shows only the MCP server, the CLI and Mongo (not the API, Identity, the web UI or OData). It says nothing about running the web app or signing in. There is no way to run a demo, and there are no tags or releases. This feature fixes the first impression without changing product behavior.

## Scope

In scope: the demo (US1), screenshots (US2), README and surrounding files (US3), changelog and release text (US4), local pre-announce checks and the threat model (US5).

Out of scope (each one is a separate decision): hosting the demo anywhere, the MSW mocked web stack, passkeys, fixing the Trivy HIGH findings, the mutation score floor. Also out of scope: any change to product behavior, the real compose files' defaults, or the real database.

## Clarifications

### Session 2026-11-08

- Q: Where does the demo seed code live, given that architecture tests keep test code out of Domain and Application and AGENTS.md forbids new test projects? -> A: In the `Cli` host, under `src/RoleRadar.Cli/Demo/`, exposed as `roleradar demo seed`. It writes through the real Mongo repositories from Infrastructure. The shared guard (`DemoModeGuard`, small, no dependencies beyond the Mongo options) lives in Infrastructure next to `MongoOptions` so the API host can call it too. Rejected alternatives:
  - *Reuse `InsightsSeed` from the Integration test project*: it is `internal` test code (Principle II and the Insights isolation architecture tests forbid production code reaching it) and it is an edge-case matrix (`age-13-interview`, `window-just-outside`, "Owner B Fixture Co"), not a showpiece. It also has four owners and exact-boundary rows that must not change.
  - *A new `RoleRadar.Demo` source project*: a new project means new layering rules, a new image target and architecture-test churn for a few hundred lines. The CLI already references Application, Infrastructure and Identity and already hosts `identity create-owner`.
  - *Seed code in Application or Domain*: puts demo data in the layers that must stay free of it.
  - *Seed code in Infrastructure*: it works, but it ships demo rows with the library every host uses. The CLI host is the thinnest place that can reach the repositories.
  - *A PowerShell or Node script writing to Mongo directly*: bypasses the repository choke point (derived fields would be hand-written, violating the AGENTS.md rule) and adds a custom script.
  - *A committed BSON or JSON dump restored with `mongorestore`*: also bypasses the choke point, goes stale when a derived field changes, and is a binary-ish blob the denylist cannot read.
- Q: How does the demo reach identity and api without hosts-file entries? -> A: Use `identity.localhost` and `api.localhost`. These names resolve to loopback in browsers and, inside the compose network, are network aliases of the identity and api services. The demo generates its own throwaway TLS certificate with those names in the subject alternative names (nothing key-like is committed). Browser reachability of `*.localhost` is a plan-phase research item (R-001) with the fallback documented there.
- Q: Which login does the demo use? -> A: The existing Identity password plus TOTP flow, unchanged (ADR 0017 and Principle I stay intact). Nothing in the web or Identity login code knows about "demo". The seed step creates one account with a fixed username and a fixed user id, a generated password and a generated TOTP key, and logs neither. Every demo command refuses to run unless the guard passes.
- Q: Is the seed relative to a fixed date or to today? -> A: To today (UTC) by default, with an `--as-of` override, so a stranger sees a live-looking 90-day window. Consequence: screenshots are reproducible by procedure, not byte-for-byte; they are regenerated by hand and reviewed, never compared in CI.
- Q: Does the real compose, the shipped images or the default configuration gain anything demo related? -> A: No. The demo is a separate compose file in `deploy/demo/` with its own project name, volume and database name. The only shipped-code additions are the `demo` CLI command group (inert unless the guard passes) and the guard call in API startup (a no-op unless demo mode (`ROLERADAR_DEMO=1`) is on).
- Q: Does the demo commit any credential? -> A: No (Principle I, ADR 0017). The seed step logs no secret. `roleradar demo credentials`, run through the `demo-cli` service, resets the demo account's password and TOTP key and prints username, password and TOTP secret once, interactively, never to a log or file. `roleradar demo totp` prints the current 6-digit code for the account. The only committed demo constants are non-secret: the fixed username, the fixed user id and the database name. No gitleaks allowlist is added. A test proves no committed file contains a demo password or TOTP secret and that the default configuration has no demo account. The screenshot spec reads the credentials from environment variables.
- Q: How is the seed idempotent without deterministic ids? -> A: By natural key (company name, posting URL, one application per posting): look up, and create with `Guid.CreateVersion7()` when missing (Principle IX). No deterministic v5-style ids. The fixed demo user id is a v7-shaped, non-secret constant set in the demo compose file and stated to be non-secret in the docs.
- Q: Where may demo constants be referenced? -> A: In production C# code only from `src/RoleRadar.Cli/Demo/` and the guard in Infrastructure. Docs, the demo compose file, the screenshot spec and tests state where they take the non-secret values from (the compose file and `docs/demo.md`); none of them holds a password or TOTP secret.
- Q: Who passes the Mongo host to the guard? -> A: Production callers pass the fixed demo host (`demo-mongo`). Only the Integration test passes its own allowed host, and the guard tests cover that case.
- Q: Which term is used for the switch? -> A: "demo mode (`ROLERADAR_DEMO=1`)" everywhere.
- Q: What does a visitor see about certificates, build time and the data? -> A: The demo uses self-signed certificates, so the browser warns once per origin (web, and `identity.localhost`); `docs/demo.md` and the README say to accept each warning once, a test checks the docs say so, and the screenshot spec ignores HTTPS errors. "Try the demo" says the first run builds four images, and the measured clean-clone-to-`/insights` time is a success criterion. The README and `docs/demo.md` state that all demo data is fictional.
- Q: Process items? -> A: The FR-012 script justification is reviewed as a pull-request review item. `docs/threat-model.md` carries the line that the demo account is throwaway and demo-only. The owner confirms the Windows results (R-001, R-009, R-012) before the demo task is considered done. The owner accepts the fixed, non-secret, v7-shaped demo user id as the one Principle IX deviation (an Identity user id, not a generated document id); it is recorded in ADR 0039.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - One-command demo with fictional data and a throwaway login (Priority: P1)

A visitor with Docker runs one documented command and gets the full web app running on their machine over a fictional dataset, with a documented demo-only account they can sign in with.

**Why this priority**: Everything else (screenshots, README "Try the demo") depends on it, and it is the only way a stranger sees the product working.

**Independent Test**: From a clean clone with no `.env` files and no hosts-file edits, run the documented command, sign in with the documented demo credentials, and open `/insights`.

**Acceptance Scenarios**:

1. **Given** a clean clone and Docker, **When** the visitor runs the single documented command, **Then** the stack comes up healthy, the seed step finishes and exits 0, and `https://localhost:<web port>` (or the documented `*.localhost` address) serves the sign-in page.
2. **Given** the demo is up, **When** the visitor runs the documented credentials command and signs in with the username, password and current TOTP code it prints, **Then** `/insights` shows non-empty funnels, stat tiles, both charts and drill-down links whose counts match the Postings and Applications lists.
3. **Given** the demo has run before, **When** the command is run again, **Then** the seed is idempotent (no duplicates) and the demo still works.
4. **Given** a developer's real stack (`roleradar-mongo` volume, database `roleradar`) is running, **When** the demo is started and later removed with its documented teardown command, **Then** the real volume, container, database and ports 27017 are untouched.
5. **Given** any configuration where the database name is not the demo database name (including the real name `roleradar`), **When** the seed command, the demo account command or the demo API starts, **Then** it refuses before any write or any served request, with an error that does not print the connection string.
6. **Given** the default compose files and default image configuration, **When** they are inspected and the Identity and API hosts start with default settings, **Then** no demo account, demo password or demo TOTP secret exists anywhere in them, and no committed file contains a demo password or TOTP secret.

### User Story 2 - Screenshots from the demo, light and dark (Priority: P1)

The owner regenerates a fixed set of screenshots from the running demo, in light and dark themes, and the README shows them.

**Why this priority**: Screenshots are what a visitor sees in the first five seconds; without them the demo is invisible to anyone who does not run it.

**Independent Test**: With the demo running, run the documented screenshot command; the expected files appear under `docs/images/`.

**Acceptance Scenarios**:

1. **Given** the demo is running and the capture switch is set, **When** the documented command is run, **Then** one light and one dark image exist for each of: Insights, an Insights drill-down result (the list a stage link lands on), the postings list, a posting detail, an application with its timeline, a company, a rendered note.
2. **Given** the capture switch is not set, **When** the normal web end-to-end suite runs, **Then** the screenshot spec is skipped and nothing is written.
3. **Given** the images are generated, **When** the owner reviews them, **Then** every image is opened and looked at before commit, and the only text in any image comes from the seed dataset and the product UI chrome.
4. **Given** the README, **When** its image references are checked, **Then** every referenced image exists under `docs/images/` and every image under `docs/images/` is referenced or listed in the image manifest.

(P3 stretch: an animated GIF of the Insights drill-down, only if it needs no new tool; otherwise dropped, see Assumptions.)

The root README becomes a front door, and the files that surround it (docs index, issue chooser, code of conduct) are consistent with it.

**Why this priority**: The README is the only page most visitors read.

**Independent Test**: Run the link check; read the README top to bottom and find, in order: pitch, badges, hero screenshot, "Try the demo", architecture, how it was built, evidence, status and limits.

**Acceptance Scenarios**:

1. **Given** the README, **When** read, **Then** it opens with a two-line pitch covering both halves (agent memory over MCP; job-search tracker with a web UI), a badge row (CI, coverage, mutation, license, .NET 10), a hero screenshot and "Try the demo" before any other section.
2. **Given** the README diagram, **When** rendered, **Then** it shows the MCP server, CLI, API, Identity, web UI, OData read seam, Application layer, Infrastructure and Mongo.
3. **Given** the README, **When** read, **Then** it has "How it was built" (Spec Kit, constitution, ADRs, architecture tests, human review gate) with open disclosure that AI agents wrote much of the code under that process, "Evidence" links (Allure report, coverage, trends, mutation dashboard), and an honest "Status and limits" (local-first by design, hosting parked, single owner).
4. **Given** the README, **When** read, **Then** it links the ADR index and one worked example from spec to PR (feature 008), and keeps the CLI and MCP reference short, with long parts moved under `docs/` and linked.
5. **Given** the move, **When** the unit tests run, **Then** `MongoOptionsReadmeConsistencyTests` still passes (the environment-variable table stays in the root README).
6. **Given** `docs/README.md`, **When** read, **Then** it indexes everything under `docs/` and is linked from the root README.
7. **Given** the repository, **When** the issue chooser is opened, **Then** it links `SECURITY.md` for vulnerability reports, disables blank issues, and the two existing forms remain.
8. **Given** `CODE_OF_CONDUCT.md` (Contributor Covenant), **When** `CONTRIBUTING.md` is read, **Then** it links the code of conduct.
9. **Given** the root README, `CONTRIBUTING.md` and `docs/README.md`, **When** the link check runs, **Then** every relative link, anchor and image reference resolves, badge URLs are well formed, and the three files give the same commands and links for the demo, the fast test loop and the review gate.

### User Story 4 - Changelog and first release text (Priority: P2)

The owner has a changelog and release text ready, and creates the tag and the GitHub Release by hand.

**Why this priority**: Visible releases signal maturity, but nothing else depends on them.

**Independent Test**: Open `CHANGELOG.md` and the release text; every feature 001 to 012 has an entry traceable to its merged PR numbers.

**Acceptance Scenarios**:

1. **Given** the git history, **When** `CHANGELOG.md` is read, **Then** it is grouped by feature (001 to 011 and 012) with PR references that exist in the history.
2. **Given** the release text, **When** pasted into a GitHub Release, **Then** it needs no editing beyond the owner choosing the tag.
3. **Given** the repository after this feature, **When** workflows are listed, **Then** no release automation was added.

### User Story 5 - Pre-announce safety checks run locally (Priority: P2)

Because the denylist is private, the owner runs checks on their own machine before announcing the repository, and a one-page threat model explains the security posture.

**Why this priority**: Prevents a one-way leak, but only matters once the owner is ready to announce.

**Independent Test**: Run the documented commands on a machine that has the private denylist; read their output.

**Acceptance Scenarios**:

1. **Given** the repository, **When** the documented gitleaks command is run over the full history with the existing config, **Then** it exits 0 or reports findings with secrets redacted.
2. **Given** the private denylist, **When** the documented denylist command is run over the whole history and over `docs/images/` metadata, **Then** it prints only counts and file names, never matched text, and exits non-zero if any match exists.
3. **Given** `docs/threat-model.md`, **When** read, **Then** in one page it states what is trusted, how untrusted posting text is handled, how authentication works, how secrets are handled and how backups are protected.

### Edge Cases

- The visitor already has something on ports 5001 to 5003: the demo uses its own documented ports and fails with a clear message, not a silent clash with the real stack.
- The visitor has no authenticator app: the credentials command prints the TOTP secret to add to one, and `roleradar demo totp` prints the current code.
- The browser warns about the self-signed certificates: accepted once per origin (web, `identity.localhost`), as the docs say.
- The visitor loses the printed credentials: running the credentials command again resets the account and prints new ones.
- The demo is started twice, or started after a failed first run: seeding is idempotent and the one-shot steps can be re-run.
- The demo volume exists from an older version of the dataset: the documented teardown removes the demo volume only (named explicitly), then the command is run again.
- Someone turns on demo mode (`ROLERADAR_DEMO=1`) against the real database: refused by the guard, proven by a test using a scratch configuration with the real name.
- Someone copies the demo compose file and changes the database name: the guard still refuses because the name is not the demo name.
- A screenshot accidentally contains a real name: the owner's image review and the history and metadata checks are the safeguards; the dataset itself contains no real names.
- Relative links inside README sections that move to `docs/`: the link check catches every broken one, including anchors.
- Markdown in the dataset's notes must not rely on raw HTML or images, which the note renderer rejects.

## Requirements *(mandatory)*

### Functional Requirements

**Demo (US1)**

- **FR-001**: The repository MUST provide one documented command that builds and starts the demo stack (Mongo, Identity, API, web UI and the one-shot setup steps) from a clean clone with no extra files and no hosts-file edits.
- **FR-002**: The demo MUST use its own compose project name, its own volume names and the database name `roleradar-demo`. It MUST NOT reference the `roleradar-mongo` volume, the `roleradar-mongo` container name, host port 27017 or the database name `roleradar`.
- **FR-003**: A one-shot seed step MUST load the fictional dataset through the real repositories, so every derived field is written at the repository choke point, and MUST be idempotent by natural key (company name, posting URL, application per posting), creating missing rows with `Guid.CreateVersion7()` and never with deterministic ids.
- **FR-004**: A shared guard MUST make the seed step, the demo account step and the demo API refuse to write or serve unless the database name is exactly the demo name, demo mode (`ROLERADAR_DEMO=1`) is on, and the server is the demo Mongo service (so the demo name on the developer's own Mongo is refused too). Production callers pass the fixed demo host; only the Integration test passes its own allowed host. The guard MUST fail closed and MUST NOT print connection strings or host names.
- **FR-005**: A test MUST prove the guard: red (refusal) for the real name, for an empty name, for a near-miss name, for demo mode off, for a host that is not the demo host, and green for the demo name with demo mode on and the demo host (plus the Integration test's explicit allowed-host case).
- **FR-006**: The demo MUST sign in through the existing Identity password plus TOTP flow with one documented, demo-only account whose only committed values are non-secret (fixed username and fixed user id). The password and TOTP key MUST be generated by the seed step and MUST NOT be logged. The sign-in code paths MUST NOT contain demo branches.
- **FR-007**: The demo account MUST exist only in the demo stack. A test MUST assert the default compose files and default configuration of the shipped images define no demo account, password or TOTP secret, that no committed file contains a demo password or TOTP secret, and that Identity and API started with demo mode on and a non-demo database refuse to start.
- **FR-007a**: `roleradar demo credentials`, run through the `demo-cli` service, MUST reset the demo account and print username, password and TOTP secret once, interactively, never to a log or file; `roleradar demo totp` MUST print the current code. Both MUST pass the guard first. A test MUST show the credentials path writes nothing to the logger.
- **FR-007b**: In production C# code, demo constants MUST be referenced only from `src/RoleRadar.Cli/Demo/` and the guard in Infrastructure, and `Cli/Demo` MUST contain no string-literal owner ids (architecture assertions). The fixed user id MUST be a v7-shaped non-secret constant set in the demo compose file.
- **FR-007c**: No client secret, session key, certificate key or any other secret MUST be committed for the demo. The demo stack MUST generate them at first start into its own named volumes, and a test MUST fail if a tracked file under `deploy/demo/` holds a secret-like value.
- **FR-008**: The demo MUST publish only loopback ports and MUST NOT expose Mongo to the host.
- **FR-009**: A documented teardown command MUST remove only the demo project's containers and volumes by explicit name.
- **FR-010**: The dataset MUST contain, all fictional: 14 companies (listed below), 48 postings across all seven dispositions (Lead 8, Unscored 3, Scored 7, ScreenedOut 7, Applied 12, Rejected 6, Closed 5), 20 applications (the 12 applied, the 6 rejected and 2 of the closed) with event timelines using every event type the Insights page counts (interview, offer, offer accepted or declined, rejection, withdrawal, follow-up, note), 6 Markdown notes, and 8 search runs, spread over about 150 days before the seed date so that both funnels, all stat tiles, the ghost rate, median response time, applications-per-week and search-run yield are non-trivial and at least one denominator is under 10 ("small sample").
- **FR-011**: All demo owner ids MUST come from `OwnerId`; no string literal owner ids are added (asserted by an architecture test over `Cli/Demo`).
- **FR-012**: Any new script MUST carry a one-line justification in this spec (see Justified additions); the justification is reviewed as a pull-request review item. The demo is orchestrated by compose plus the existing CLI.

**Screenshots (US2)**

- **FR-013**: A Playwright spec gated by an environment variable (same pattern as the visual baseline spec) MUST capture, in light and dark, Insights, an Insights drill-down result, the postings list, a posting detail, an application with its timeline, a company and a rendered note, into `docs/images/`.
- **FR-014**: The spec MUST be skipped, with a reason, when the variable is not set, and MUST refuse to run against anything but the demo address.
- **FR-015**: The documented procedure MUST state that the owner views every image before commit, and that the seed's names are the only source of text in them.
- **FR-015a**: The Playwright spec MUST read the demo credentials from environment variables and MUST ignore HTTPS errors (self-signed certificates).
- **FR-016**: A manifest of expected image names MUST exist and a check MUST fail if `docs/images/` holds an unlisted file or the README references a missing file.

**README and files (US3)**

- **FR-017**: The README MUST contain, in order: pitch, badges, hero image, "Try the demo" (which says the first run builds four images, that the browser warns about self-signed certificates and to accept the warning once per origin, web and `identity.localhost`, and that all demo data is fictional), architecture diagram, "How it was built", "Evidence", "Status and limits", links to the ADR index and the feature 008 worked example, then a short CLI and MCP reference.
- **FR-017a**: `docs/demo.md` MUST state the certificate-warning instruction and the fictional-data disclaimer, and a test MUST check both statements are present in `docs/demo.md` and the README.
- **FR-018**: The badge row MUST use: the CI workflow badge, `https://mwalczyk81.github.io/roleradar/badges/coverage.svg`, `https://badge-api.stryker-mutator.io/github.com/mwalczyk81/roleradar/main?module=web-lib`, the license badge and a .NET 10 badge. "Evidence" MUST link `https://mwalczyk81.github.io/roleradar/` (Allure report, coverage, trends, mutation dashboard).
- **FR-019**: The environment-variable table MUST stay in the root README with the default connection string unchanged so `MongoOptionsReadmeConsistencyTests` passes; other long sections (MCP client registration, tool table, Insights details, operations, backup and restore) MUST move under `docs/` and be linked.
- **FR-020**: `docs/README.md` MUST index every file under `docs/` (ADR index, API and OData docs, operations runbooks, integrations, repo settings, threat model, denylist example, constitution changelog, the root changelog, pre-announce checks).
- **FR-021**: `.github/ISSUE_TEMPLATE/config.yml` MUST disable blank issues and link `SECURITY.md` for vulnerability reports; both existing forms MUST stay.
- **FR-022**: `CODE_OF_CONDUCT.md` MUST be the Contributor Covenant (version stated, contact method pointing to the existing security contact, no new address) and be linked from `CONTRIBUTING.md`.
- **FR-023**: An automated check MUST verify that every relative link, anchor and image reference in the root README, `CONTRIBUTING.md` and `docs/README.md` resolves, that badge URLs are well formed https URLs, and that the three files agree on the demo, fast-loop and review-gate commands. It MUST run in CI.

**Releases (US4)**

- **FR-024**: `CHANGELOG.md` MUST be built once from the conventional-commit history, in Keep a Changelog format with an Unreleased section and 0.1.0, summarizing features 001 to 012 by capability (each entry names its feature and PR numbers), and a v0.1.0 release text MUST be drafted in `specs/012-front-door/release-v0.1.0.md` for the owner to paste when creating the tag and release (owner direction, 2026-11-09). No release automation is added; the owner creates the tag and the release.

**Safety (US5)**

- **FR-025**: The docs MUST give a one-time full-history gitleaks command using the existing `.gitleaks.toml`, with redaction on.
- **FR-026**: The docs MUST give a command that runs the private denylist over all history (commit content and commit messages) and over `docs/images/` metadata and prints only counts and file names. It MUST never print matched text and MUST handle comment lines, blank lines and a BOM in the denylist the same way the existing hook does.
- **FR-027**: `docs/threat-model.md` MUST be at most one page and cover trust boundaries, untrusted posting text, authentication, secrets and backups, and MUST note that the demo account is throwaway and demo-only.

### Justified additions (new scripts or tools)

- None for the demo, screenshots, link check or releases: compose plus the existing CLI, the existing Playwright setup, and a Vitest test under `web/tests/tooling` (markdownlint cannot check link targets).
- Extending the existing `scripts/denylist-check.ps1` with history and image-metadata modes: one-line justification: the denylist's comment, blank-line and BOM handling and the counts-only output rule cannot be expressed safely as a pasted one-liner, and reusing the script keeps one parser for the private file.
- Two compose one-shot services, each running a pinned stock image with an inline command and no custom script: `demo-certs` (generates the throwaway TLS certificate and key into the demo volume; nothing key-like is committed) and `demo-secrets` (generates the OIDC client secrets and the session key into the demo volume; no secret is committed). One-line justification: the real apps require these values and committing any fixed value would be a committed secret (Principle I). Both are reviewed in the pull request under FR-012.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001a**: The clean-clone-to-`/insights` time is measured on the owner's machine from `git clone` to a loaded `/insights` with seeded data (first run, four images built); the number is recorded in the PR description and stated in the README as a typical time.
- **SC-001**: From a clean clone, the documented demo command ends with all services healthy and the seed step exited 0, and the sign-in and `/insights` page load with the seeded data (non-empty funnels; every drill-down count equals the matching list's row count), in under 10 minutes cold and under 3 minutes with warm image layers.
- **SC-002**: The guard test class is red (refusal) for each scratch configuration naming the real database `roleradar`, an empty name and a near-miss name, and green only for `roleradar-demo` with demo mode on. Output of the test run shows the case count.
- **SC-003**: A repository-wide search of `deploy/docker-compose.yml`, `deploy/docker-compose.apps.yml` and the shipped image configuration finds no demo username, password or TOTP secret, and a test asserts it, together with no demo password or TOTP secret in any committed file; starting Identity and API with demo mode on and a non-demo database is refused.
- **SC-004**: While the demo runs next to the real stack, `docker volume ls` shows `roleradar-mongo-data` unchanged and `docker compose -p roleradar-demo down -v` leaves it in place (checked by name, not by running anything against the real database).
- **SC-005**: The screenshot command produces exactly the manifest's files (7 views x 2 themes = 14) and the normal e2e run produces none.
- **SC-006**: The README link check passes in CI for the three files, and fails when a link, anchor or image reference is deliberately broken (shown red first).
- **SC-007**: `MongoOptionsReadmeConsistencyTests` passes after the README is rewritten, and `pre-commit run --all-files` passes.
- **SC-008**: The README, read cold, lets a visitor reach a running demo in four documented steps (clone, start the stack, run the credentials command, sign in), and the root README is no longer than 200 lines.
- **SC-009**: The full-history gitleaks command and the denylist history and image-metadata commands are documented, run by the owner locally, and their outputs contain only counts and file names (checked by the owner reading the output once).
- **SC-010**: `CHANGELOG.md` lists features 001 to 012 and every PR number in it exists in `git log`.

## Assumptions

- Docker with Compose v2 is the only prerequisite for the demo; no .NET SDK or Node is required to run it.
- The Linux CI image is the gate for the web parts; the demo itself is verified locally by the owner and by a CI job only if one is cheap (decided in the plan).
- The owner confirms the Windows results (R-001, R-009, R-012) before the demo task is considered done; CI covers Linux.
