## D3. Ratchet policy (decided in the spec, mechanism here)

- **Policy**: `quality/mutation-minimums.json` holds a floor per project. First run is report-only (break at 0). After the first recorded run the floor is set to that score rounded down to a whole percent. Afterwards the nightly job fails below the floor, and a check fails any change that lowers a floor relative to the base ref. Raising is a deliberate reviewed commit; automation never edits the file.
- **Mechanism**: `scripts/check-mutation-minimum.ps1` has two modes. `-Score` mode compares a score against the floor (used by the nightly job). `-BaseRef` mode diffs the file against `origin/main` and fails on any decrease or removed project (runs on pull requests, cheap, no mutation). Contract in [contracts/mutation-minimums.md](contracts/mutation-minimums.md).
- **Alternatives**: Stryker `break` threshold in config (rejected as the only mechanism: it is edited in the same place as the floor and cannot detect lowering across commits); automatic PR to raise floors (rejected: bot commits).

## D4. Nightly workflow shape

- **Decision**: new `nightly-quality.yml`: `schedule` (daily, 02:00 UTC) and `workflow_dispatch`; top-level `permissions: {}` then per-job grants (`contents: read`; the Pages publish job alone gets `contents: write`); `concurrency` group so overlapping runs queue and never publish concurrently, `cancel-in-progress: false`; every job has `timeout-minutes`; actions pinned by SHA via the existing `verify-action-pins.ps1` rule; checkout with `persist-credentials: false`. Triggers are exactly three: `schedule`, `workflow_dispatch`, and `pull_request` with `paths: ['.github/workflows/nightly-quality.yml']` (the validation run). Never `push`, never `pull_request_target`.
- **Validation run (owner decision)**: on the `pull_request` path every job carries `if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository`; the dashboard publish step and the Pages publish job carry `if: github.event_name != 'pull_request'` and are the only places a secret or `contents: write` is referenced, so no secret is reachable on the PR path; jobs on that path have `contents: read` only; reports upload as artifacts; the concurrency group includes the event name so a validation run never cancels or queues behind a nightly. A Vitest test (`web/tests/tooling/workflow-triggers.test.ts`, using the `yaml` package pinned as a web devDependency, or an already-pinned parser if one exists; T003 decides) asserts the trigger block is exactly this shape and that no `secrets.` reference sits outside the guarded steps. It is written first and shown red against the missing workflow file.
- **What to read from the validation run** (used by the tasks marked "after the PR's validation run"): the run URL and commit; for the web lib (the only mutation project while .NET is deferred, D1) from the job summary and the uploaded `mutation-score.json`: score, killed, survived, no coverage, timeout, ignored; job durations from the run page (sets `timeout-minutes`); the HTML report artifacts opened locally for the survivors list; the log text searched for the dashboard key variable name followed by a value (SC-004 without the secret); the Allure report artifact downloaded and opened to confirm the stacks present and, for the seeded failing e2e test, its screenshot and trace. Pages-dependent checks (trends after two runs, Pages publish) cannot be read from a pull request and are recorded as post-merge owner steps.
- **Dashboard secret**: Secrets cannot be tested in `if:`. The dashboard reporter is added to the Stryker command only when `has_key` is true. When false, the summary writes "Stryker Dashboard publish skipped: secret not configured" and the artifact upload still runs. A dashboard rejection (bad key) is reported but does not fail the score check.
- **Budget and scope cut**: each job's `timeout-minutes` is the budget; on expiry the failure text points to this section. To cut scope, in order: (1) narrow `mutate` globs per project, (2) raise the mutation level threshold from Standard to Basic, (3) drop to a mutant sample using Stryker's mutation filters, (4) shard across matrix jobs by file group. Initial budgets and the first measured durations: **PENDING** (record from the first run).

## D6. Run summaries from pipeline numbers

- **Decision**: `scripts/build-run-summary.ps1` consumes structured inputs and writes Markdown to `GITHUB_STEP_SUMMARY` (and stdout locally). Inputs: TRX files for test counts per lane (add `--logger "trx;LogFileName=<lane>.trx"` to the existing `dotnet test` calls; counts come from the TRX `Counters` element, not console scraping), the merged Cobertura XML for coverage per project (the Cobertura `package` element is per assembly), the `docker image inspect` sizes the gate already computes, and the Trivy JSON reports plus scan-test counts already read.
- **Gate**: the gate already computes these values in variables. It will additionally write one `gate-summary.json` and render both its console text and the Markdown table from it, so the table and the printed lines cannot diverge.
- **Failure behavior**: any missing or unparsable input throws; the table cell reads `unavailable` and the step fails. No defaults. Table contract in [contracts/run-summary.md](contracts/run-summary.md).
- **Why TRX**: the gate's regex over console output breaks on any wording change; TRX is a stable machine format and is also the input for the .NET Allure fallback (D10).

**Implemented (Story 2, 2026-11-07)**:

- `ci.yml` `ubuntu-build-and-test` adds `--logger "trx"` to the full `dotnet test` run (the lane comes from the assembly name inside each TRX, so default file names are fine), records image sizes from `docker image inspect` into `TestResults/images.json`, and runs `scripts/build-run-summary.ps1` with `if: always()`. Only the inputs whose steps ran are passed (backend steps: TRX and merged Cobertura; image steps: images and Trivy reports), so a missing expected input shows as `unavailable` and fails the step. The normalized numbers are written by the new `-JsonOutputPath` (tests, coverage, images, scan; null for an unavailable value) and uploaded as the `run-summary` artifact for the metrics job.
- Verified on real TRX files from `dotnet test` (local): Architecture 46 passed and Contract 215 passed, matching the test output lines. The fixtures used by the unit tests are stored as `*.trx.fixture` and the tests write real `.trx` files into a temp folder, so no `.trx` file is committed.
- The gate renders its console lines from `scripts/format-gate-summary.ps1` and its Markdown file (`TestResults/gate-summary.md`) from `build-run-summary.ps1 -GateSummaryFile`, both reading the one `gate-summary.json` that `review-gate.ps1` writes from the values it measured (per-lane passed, failed and skipped parsed from the test output, coverage including per-project and branch rates from the merged Cobertura, image sizes in bytes, scan counts, the images lane). Trade-offs accepted: a cache entry unused for 7 days is evicted (the nightly touches it daily, so it stays alive), a cache is not durable (a reset restarts trends, nothing is lost that matters), and two runs finishing at the same moment can lose one run's line. The published Allure site itself is on gh-pages (`allure/`), without the history file.
- **`historyLimit` = 30**, set in `web/allurerc.mjs` with the reasoning in its header: about 0.6 MB per run at 659 tests (measured), about 2.4 MB per run for the real suite of about 2,600 tests, about 70 MB at the limit (about a month of nightlies; busy days on main shorten the window because every publishing run adds a line). - Tests whose subject is not a lib module moved to `web/tests/tooling/` (git mv, same depth, so relative imports are unchanged): allure-sanitize, check-combined-report, metrics-record, mutation-ratchet, vitest-config, trends, workflow-triggers, workflow-privacy, playwright-config, vite-config, odata-metadata-drift, insights-e2e-isolation, contrast, style-census, kit-no-style-attributes, root, root-theme-render, entry.server and server. The ordinary Vitest include (`tests/**`) still runs them.
- `web/tests/tooling/stryker-include-scope.test.ts` scans every file the Stryker include matches (static scan of runtime imports, dynamic imports and path-building calls with a parent segment) and fails on any reference outside `web/`. `import type` is erased and ignored. The one allowed outside folder is `contracts/`, which `scripts/stryker-run.mjs` copies next to the sandbox. The scan is conservative: a `__dirname` path with `../` that stays inside `web/` is still reported, and the author restructures it.
