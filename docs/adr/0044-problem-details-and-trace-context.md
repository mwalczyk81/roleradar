# ADR 0044: RFC 9457 Problem Documents and W3C Trace Context

- **Status**: Accepted (2026-11-10)
- **Date**: 2026-11-10
- **Feature**: `014-standards-first` (story P2, Jira RR-74, RR-78, RR-64)

## Context and Problem Statement

Feature 013 gave the API a private error envelope (`{ ok, errorCode, message, details, correlationId }`, ADR 0018 section 2) and a private correlation id carried in a custom `X-Correlation-ID` header (ADR 0041). Both are mechanisms a standard already covers: RFC 9457 defines the error document and its media type, and W3C Trace Context defines the id and its header. Principle X (Standards First) asks for the standard unless a recorded reason says it does not fit. Nothing is tagged yet and every consumer is internal, so the cost of changing the contract is lowest now (RR-62 would make it expensive).

Two defects were found in the web's handling of the old envelope and are closed by this change (RR-64): `mapApiError` read `details[].message` where the contract field is `issue`, so inline field errors never showed, and it compared upper-case error codes to the lower-case ones the server sends.

## Decision Outcome

### Problem documents (RFC 9457)

- **Every error is `application/problem+json`**, built with the ASP.NET Core platform features: `AddProblemDetails` with a `CustomizeProblemDetails` callback, `UseStatusCodePages` (so an empty 401, 403 or 404 body written by authentication, authorization or routing gets the same document), `TypedResults.Problem` and `TypedResults.ValidationProblem`, and an `IExceptionHandler` for unhandled exceptions. The envelope, `ErrorResults` and the private result wrapper are deleted.
- **Members.** `type`, `title`, `status`, `detail` (400, 404, 409, 500, 503), the extension `errorCode` (lower case, the value the web switches on), the extension `traceId`, and `errors` on a validation failure (`{ field: [issue, ...] }`, the platform's `ValidationProblemDetails` shape; a nested field name such as `contact.email` is kept verbatim). `docs/api/problems.md` lists every code.
- **Mapping from the envelope.** `ok: false` became the HTTP status and `status`; `errorCode` stayed and also builds `type`; `message` became `detail`; `details[{ field, issue }]` became `errors`; `correlationId` became `traceId`. This is a breaking change, allowed because nothing is tagged and every consumer is internal. Message texts are unchanged, and the 503 and 500 bodies are still fixed text with no exception text, connection detail or command.
- **OData routes too.** The OData JSON error response (`{ "error": { "code", "message", "target", "details" } }`, OData JSON Format 4.01) was **the alternative compared** for the `/odata` routes. RFC 9457 was preferred because the only consumer is the typed web client, so one format gives it one parsing path and one error model in the contract tests. **The cost:** a generic OData client (a spreadsheet or BI tool) sees a problem document instead of the OData error shape. RoleRadar is single-owner and local-first and does not publish `/odata` to third-party clients, so the cost is accepted.
- **`traceId` is the bare trace id, not the platform default.** Measured on 2026-11-10: the platform writes `Activity.Id` (the full `00-<trace>-<span>-<flags>` string), whose span part differs on every hop, so it would never match across the web, API and Identity logs. The `CustomizeProblemDetails` callback sets it to `Activity.Current.TraceId` (32 hex characters). The generated client carries `errorCode` and `traceId` as typed strings through an OpenAPI schema transformer, so the web needs no cast.
- **`Accept` is not negotiated for our own errors.** The platform's `IProblemDetailsService` writes nothing when the client's `Accept` header excludes JSON. Results built by `ApiProblems` therefore go through `TypedResults.Problem` directly, so an error always has a body; the service writes the platform-originated ones (status-code pages), through the same callback.

### The problem `type` identifier

- **Chosen (owner decision, 2026-11-10): a documentation URL in the public repository**, one anchor per error code: `https://github.com/mwalczyk81/roleradar/blob/main/docs/api/problems.md#<errorCode>`. RFC 9457 section 3.1.1 prefers a `type` that resolves to human-readable documentation, and this one does. The base is a single constant, `ProblemTypes.TypeUriPrefix`, so it can move if the API is hosted (epic RR-2). A status with no code of ours (405, 415) keeps the platform default. The web switches on `errorCode`, never on `type`, so moving the URL changes no behavior.
- **Cost:** the identifier is tied to the repository location. A rename or move of `docs/api/problems.md`, or a change of the repository owner or branch, changes the value; the constant and the page move together.
- **Alternatives compared.** An RFC 4151 tag URI on the authority `mattwalczyk.com` (`tag:mattwalczyk.com,2026:roleradar:problem:<errorCode>`): permanent and needs no hosting, but it never resolves, so a reader cannot follow it to documentation. An informal `urn:roleradar:` namespace: not a registered URN namespace (RFC 8141), the kind of home-grown identifier this feature removes. The platform's default RFC 9110 URLs: they describe the status, not our codes.

### Trace context (W3C)

- **The id is the bare trace id** (32 lower-case hexadecimal characters, not all zero), everywhere. There is no second id and no custom header.
- **.NET.** `System.Activity` and the built-in `DistributedContextPropagator`. ASP.NET Core extracts a valid inbound `traceparent` and starts the request activity itself (a malformed one is ignored and a new trace is started), and `HttpClient` propagates it, so there is no middleware. One helper, `RoleRadar.Observability.TraceIds`, returns the current trace id (generating one where no activity exists, as a background task). The CLI starts one activity per run and the MCP host one per tool call, with a random trace id (`ActivityTraceId.CreateRandom()`), so every log record and audit entry of a run or call shares one id (stderr only in the MCP host, Principle VI).
- **Web.** `@opentelemetry/api` 1.10.0 and `@opentelemetry/core` 3.0.0 (Apache-2.0, no SDK, no exporter, no instrumentation; nothing leaves the machine, 013 FR-028). The W3C propagator validates an inbound `traceparent` and formats the outbound one; ids come from `node:crypto`. Compared: a hand-written `traceparent` (about 12 lines, but it re-learns the edge cases: all-zero ids, version `ff`, upper case, the flags byte, and it would need its own ADR) and the full OpenTelemetry SDK with its HTTP and undici instrumentations now (that is feature 015, with its preload flag, sampling and exporter policy, and is not needed to deliver one id).
- **Feature 015 builds on `@opentelemetry/api`.** Its SDK registers under the same API package, so the calls written here keep working. 015 adds the SDK and the instrumentations, which create the server span and inject `traceparent` themselves, and deletes only the manual root span context and the explicit injection written here. The trace id format, the `traceId` log field, the problem document member and the audit value do not change, so the id is not migrated twice.
- **Header rules.** Only `traceparent` is read. A malformed, all-zero, upper-case, oversized or extra-field value is discarded, never logged, and replaced. `tracestate` is neither used nor forwarded. **`X-Correlation-ID` is gone**: it is not read, written or returned, and an inbound one is ignored (no client needs it; an ADR would name one). **No response header returns the trace id**: it reaches a client in the problem document of an error. A browser navigation to Identity gets Identity's own trace.
- **Logs.** The JSON field `correlationId` is now `traceId` (the OpenTelemetry name for the same value, so 015 does not rename it again); in text mode the bracket shows the trace id. The console formatter reads `Activity.Current` instead of a logging scope key. Records written with no active request carry no `traceId`, as before. The per-request `RequestCompleted` record stays, now written by a middleware that does nothing else.
- **Audit.** The stored field keeps its name `request_correlation_id` (audit is append-only; renaming means migrating data, so it is naming debt, accepted) and holds the trace id for new entries. Old entries keep their old-format values and still list through `audit list` (spec scenario 9, a contract test). The Application property `IRequestContext.CorrelationId` keeps its name while carrying the trace id. `details.after.correlation_id` (ADR 0033, a posting event to application event link) is a different concept and is untouched.

## Consequences

- **Good:** one standard error document and one standard id; the hand-written envelope, both correlation middlewares, the id rules, the header handling and the web's id helpers are gone (source scans enforce it, SC-007); inline field errors work again and the error code comparison is case-correct (RR-64); the id a person finds in a problem document finds the web, API and Identity log lines and the audit entry of the same request.
- **Bad:** a breaking change to the error body, the correlation header and the log field; a generic OData client sees a problem document; the `type` URL is tied to the repository; the audit field name and the `IRequestContext.CorrelationId` name no longer say "trace id" (naming debt).
- **Packages:** `@opentelemetry/api` 1.10.0 and `@opentelemetry/core` 3.0.0 on the web; no NuGet package (the platform features are in the shared framework).
- **Supersedes in part:** [ADR 0018](./0018-rest-api-style-and-owner-mapping.md) section 2 (the error envelope) and the correlation section of [ADR 0041](./0041-operability-logging-correlation-health.md) (the log record, health, outage and redaction decisions of 0041 stand).
