# ADR 0038: Reporting From Pipeline Numbers, With One Combined Allure Report

- **Status**: Accepted
- **Date**: 2026-11-07 (revised 2026-11-08)
- **Feature**: `011-test-quality-reporting`

## Context and Problem Statement

The repository states test counts and a coverage figure in prose. Those numbers go stale, and a reader cannot tell which command produced them. The pipeline already produces the real numbers (TRX files, Cobertura, image sizes, Trivy reports); nothing collected them, kept their history, or showed three test stacks (xUnit, Vitest, Playwright) in one place. Publishing is a new surface on a public repository, so what reaches it matters as much as what it shows.

## Decision Outcome

- **Run summaries come from the run's own outputs.** `web/scripts/metrics-record.mjs summary` reads TRX files (test counts per lane, from the TRX counters, not from console text) and ReportGenerator's `Summary.json` (`JsonSummary`: overall and per-assembly coverage), and writes two tables to the job summary next to ReportGenerator's own Markdown summary. A missing or unparsable input shows as `unavailable` and fails the step; no default is substituted; text read from reports is escaped before it reaches Markdown (tested with a hostile TRX fixture). Image sizes and scan counts are not in the CI summary, because neither the metrics record nor the trends page uses them. The review gate renders its console lines inline from the object it writes to `gate-summary.json` and keeps printing image sizes and scan counts.
- **Coverage HTML and badge.** ReportGenerator (already pinned) writes the HTML report and the badge SVGs; the HTML is a 14-day artifact on every run. On main the badge is published as a static SVG on the gh-pages branch, which needs only the publish job that already exists. The Stryker Dashboard covers the mutation badge when its secret exists; there is no second badge pipeline.
- **Metrics history and trends page.** One JSON line per main run (test counts per lane, coverage, job durations from `gh run view --json jobs`, and the latest nightly mutation score with its own run date and commit) is appended to `metrics/metrics.jsonl`. The publish job checks out the existing gh-pages tree, `web/scripts/metrics-record.mjs record` appends to the existing file unless that commit is already recorded and writes the whole file to a separate output folder, and `peaceiris/actions-gh-pages` (v4.1.0, SHA pinned) copies it with `keep_files`. A static page (`pages/metrics/`, no third-party script, strict CSP, values inserted as text) draws sparklines and shows a visible count of unreadable lines. There is no skip logic: pushing to the branch works whether or not GitHub Pages is enabled, and the publish job summary says what the owner must enable.
- **Playwright failure evidence.** A screenshot on failure and a trace on the first retry; uploaded only when a job fails; 14 days for the fictional-data job and 7 days for the real-stack job, whose traces can show real-looking sessions. None of it reaches the published site.
- **One combined Allure report per publishing run.** Allure 3 (`allure` 3.22.1, Node) reads Vitest and Playwright results written by `allure-vitest` and `allure-playwright` 3.14.0 and, for .NET, the native JUnit output of each xUnit v3 test executable (a plain `-junit` step in each workflow). No csproj change and no Microsoft Testing Platform migration: `Allure.Xunit.v3` exists only as a preview (3.0.0-preview.1) and works only in Microsoft Testing Platform mode, so it is revisited when it has a stable release. A TRX converter is the fallback only if the JUnit output loses something the report needs (today it loses nothing the report uses; it has no traits, steps or attachments). A final job that always runs, in `ci.yml` and in the nightly workflow, builds the report from the stack jobs' results, so a failed stack still yields a report. It runs no tests. `web/scripts/check-combined-report.mjs` fails when a source whose job succeeded is missing, empty or absent from the merged results, or when the report counts fewer tests than were fed in. The ordinary CI report covers the fast .NET lanes; the nightly adds the Integration lane and runs the end-to-end suite five times for flake detection.
- **Privacy.** Everything is sanitized before it is merged or published (`web/scripts/allure-sanitize.mjs`): real-stack results keep only pass or fail, names and timings (every attachment is removed at any nesting depth); fictional results keep screenshots and plain text but never trace archives; all results lose absolute paths, user names and host names (JUnit XML included, where the test assembly path and the machine name appear). The merged results and the generated site are leak-checked, reporting the file and rule and never the matched text. Tests fail if a sanitizer misses a nested attachment (shown against a no-op and a top-level-only sanitizer) or if the workflows would upload raw real-stack results or merge unsanitized input.
- **History location.** The Allure history file is `allure-history/history.jsonl` in the gh-pages tree. The report job reads it from the branch (a missing branch or file starts a new history), generates, and uploads the updated file as a one-day artifact; the publish job on main (and the nightly publish job) writes it back with `keep_files`. It is capped with `historyLimit: 30` (about 0.6 MB per run at 659 tests, about 70 MB at the limit for the real suite), documented in `web/allurerc.mjs`. Revised from an earlier decision to keep it in the Actions cache: the owner chose one tree for all published state. The cost is that every publish commits a new multi-megabyte version of the file, so the branch history grows (see Consequences), and the file is served publicly with the site (it holds sanitized test names, statuses and timings, like the report).
- **Least privilege and supply chain.** Only the publish jobs have `contents: write`, and neither runs on a pull request or a fork. `peaceiris/actions-gh-pages` pushes with the job token and nothing is persisted by any checkout (`persist-credentials: false` everywhere). Every action is pinned by SHA, every package at an exact version (`allure` at the newest release at least 14 days old, because the repository's own Dependabot cooldown is 7 days), and `zizmor` and the pin verification pass.
- **Standard tools over custom scripts (revision of 2026-11-08).** The run summary, metrics record, mutation ratchet and combined-report check are Vitest-tested `.mjs` files under `web/scripts/`; publishing is `peaceiris/actions-gh-pages`; lint is `Invoke-ScriptAnalyzer` called directly. No third-party test-report action is used: none documents how report text is escaped, they all need `checks: write`, and none helps the local gate. AGENTS.md now says a new script needs a one-line justification in the spec and CI-only logic goes in `.mjs` tested by Vitest.
- **Generated output is never committed.** `TestResults/`, `*.trx`, `allure-results/`, `allure-report/`, `StrykerOutput/` and the CI working folders are ignored; CI generates results fresh and uploads them as artifacts, and nothing reads a committed TRX.

### Consequences

- Good: the numbers shown are the numbers the pipeline measured, with a history, and the same object feeds the gate's console lines.
- Good: one report shows all three stacks, with flakes and history, and a stack cannot vanish from it unnoticed.
- Good: a public report cannot carry traces, real-stack attachments, local paths or machine names, and tests fail if the workflows or the sanitizer regress.
- Bad: the fast .NET lanes run twice in CI (once for the gate, once for JUnit), about two extra minutes.
- Bad: the gh-pages branch grows. Each publish commits the Allure history file again (up to about 70 MB at the cap for the real suite), so the branch history can reach hundreds of megabytes over months; squashing it to a single commit now and then is an owner action (peaceiris `force_orphan` can do it, deliberately). `allure/` and `coverage/` are replaced each publish, so only the history file and `metrics.jsonl` accumulate.
- Bad: three deploy steps per publish mean three commits; and the CI main publish and the nightly can read the same history and the later publish overwrites the earlier one's run (trends lose one point, nothing else).
- Bad: `ci-gate` now depends on the report job, so an Allure infrastructure failure can block a merge.
- Bad: the JUnit path gives .NET results no traits or steps; adopting `Allure.Xunit.v3` later would add them at the cost of moving to Microsoft Testing Platform.
